# 살아 있는 세션 조정과 통신 예산

## 목적

같은 저장소, 공유 하네스, 공용 런타임을 여러 세션이 동시에 다룰 때 상대를 추측하지 않고 확인하되,
세션끼리의 통신이 사람의 시야 밖에서 무제한으로 이어지지 않게 한다. 이 문서의 제한은 세션 간 메시지에
적용하며 사람이 보낸 프롬프트, 세션 목록 조회와 읽기 전용 관측 자체는 메시지 수에 포함하지 않는다.

## 용어

- **살아 있는 세션**: 종료되지 않았고 후속 메시지를 받을 수 있는 독립 실행 문맥. 지금 모델 턴을
  실행 중인지와는 다르다.
- **세션 간 메시지**: 한 세션·에이전트가 다른 살아 있는 세션·에이전트에 전달한 하나의 payload. 한 번에
  여러 대상에게 보내면 대상 수만큼 센다.
- **조정 트랜잭션**: 한 번의 사람 프롬프트 아래 특정 충돌 위험이나 협업 판단 하나를 닫기 위한 세션 간
  메시지 묶음. 사람이 새 프롬프트를 보내면 이전 tx를 닫고 후속 통신은 새 tx로 시작한다.
- **새 값**: 직접 질문에 대한 답, 새 실측, 변경된 상태, 결정에 필요한 근거 또는 산출물 포인터.
  동의·감사·인사·이미 전달한 내용의 반복은 새 값이 아니다.

## 언제 살아 있는 세션을 확인하는가

모든 시작을 막는 게이트로 쓰지 않는다. 다음처럼 잘못 판단하면 기록 손실, 덮어쓰기 또는 공유 자원 충돌이
생기는 경계 직전에만 확인한다.

1. 확인 커서나 `ack`처럼 다른 세션이 아직 보지 못한 항목을 되돌릴 수 없이 건너뛰게 하는 상태 전진
2. `ISSUES.md`, `AGENDA.md`, `INDEX.md`, 공통 canon처럼 append-only가 아닌 공유 파일 수정
3. worktree·브랜치·캐시의 일괄 정리
4. dev server, devstack, 포트, 테스트 환경처럼 동시에 하나만 점유해야 하는 공유 런타임의 시작·중지·교체

런타임이 제공하는 세션 등록부와 직접 메시지 기능이 있으면 다음 순서로 확인한다.

1. **생존 여부와 정체성 정보를 분리해 본다.** `isRunning`, 최근 활동 시각, 프로세스 mtime은 현재 턴이나
   흔적을 나타낼 뿐 세션 생존의 정본으로 사용하지 않는다.
2. 대상은 정규화한 현재 작업 디렉터리에서 얻은 `project-id`와 worktree 경로로 식별한다. 제목, 대화명,
   브랜치명, 임의 slug만으로 대상을 고르지 않는다.
3. 같은 디렉터리의 세션이 둘 이상이면 런타임의 안정적인 session id와 현재 task·소유 경로를 함께
   대조한다. 그래도 구별되지 않으면 쓰기를 멈추고 사용자에게 알린다.
4. 위험 경계가 겹치는 세션에 현재 소유 파일·커서·공유 자원과 예상 종료 조건을 직접 묻는다.

세션 등록부나 직접 메시지 기능이 없거나 다른 머신·IDE·사람의 수동 편집을 포괄하지 못하면 “다른 세션이
없다”고 단정하지 않는다. `INDEX.md` 규칙 1과 16의 보수적인 직렬·Git 경계를 적용하고, 안전한 소유권을
확인할 수 없으면 읽기와 기록까지만 수행한 뒤 사용자에게 알린다.

## 공유 쓰기의 선후

- append-only가 아닌 공유 파일이나 단일 공유 자원은 응답을 먼저 받아 소유권을 확인한 세션 하나만
  변경한다. 나머지 세션은 읽기·자기 기록만 수행한다.
- 소유 세션은 변경을 커밋하거나 자원을 해제한 뒤, 파일·커밋 또는 자원 상태를 붙여 `회신 불요` 메시지로
  다음 세션에 넘긴다. 다음 세션은 디스크와 Git 상태를 다시 읽은 뒤 자기 변경을 적용한다.
- 무응답을 쓰기 허가로 해석하지 않는다. 안전한 다른 경로가 없으면 사용자에게 알리고 멈춘다.
- 대기가 등록된 task·request를 실제로 막으면 현재 issue·request 요약에 차단 원인과 해제 주체를
  기록한다. 단순한 짧은 대기를 위해 새 상태값이나 사람 판단용 `AGENDA.md` 행을 만들지는 않는다.

## 메시지를 보내는 조건과 종료 신호

- 새 값이 있을 때만 메시지를 보낸다. 단, 직접 질문에 대한 짧은 답은 상대의 대기를 해제하므로 새 값으로
  취급한다.
- 메시지에는 질문 또는 결론, 확인 가능한 근거와 산출물 포인터, 상대에게 필요한 다음 행동을 넣는다.
- 단순 수신 확인, 감사, 동의 반복과 종료 인사는 보내지 않고 자기 저널에만 기록한다.
- 마지막 유효 메시지에는 필요하면 `회신 불요`를 표시한다. 이 신호를 받은 세션은 답하지 않는다.
- 의견이 갈리면 메시지 왕복으로 확정하지 않는다. 각 근거를 request에 기록하고 `AGENDA.md`로 사용자
  판단을 요청한다.

## 독립된 두 통신 예산

두 제한은 서로 다른 위험을 다루므로 어느 하나가 다른 하나를 대체하거나 초기화하지 않는다.

| 제한 | 세는 범위 | 중단 시점 | 막는 위험 |
|---|---|---|---|
| 트랜잭션 총량 | 같은 tx의 모든 세션·양방향 메시지 합계 | 총 10건에 도달하면 종료. 11번째 전송 금지 | 여러 세션으로 퍼지는 무제한 fan-out |
| 사람 프롬프트 이후 수신량 | 한 세션이 사람의 마지막 직접 프롬프트 뒤 받은 세션 간 메시지 | 5번째 수신 직후 일시 중단 | 한 세션이 사람의 시야 밖에서 장시간 진행 |

### 조정 트랜잭션당 총 10건

1. 개시자는 첫 메시지 전에 tx id `<topic>-YYYYMMDDTHHMMSSZ`를 만든다. `<topic>`은 짧은 kebab-case,
   타임스탬프는 UTC다. 메시지와 로그에서는 `tx:<id>`로 표기한다.
2. 응답자와 후속 세션은 받은 tx id를 그대로 사용한다. peer 메시지나 자동화 신호를 받았다는 이유로,
   또는 상한을 초기화할 목적으로 새 tx를 만들지 않는다.
3. 각 메시지는 `[tx:<id> <n>/10]` 헤더를 싣는다. 첫 전달은 `1/10`이고, 송신자는 관측한 가장 큰 번호에서
   1을 더한다. 한 번에 N개 세션에 fan-out하면 N개 전달을 각각 센다.
4. 중앙 조정 세션이 있는 실행 환경에서는 개시자가 전체 카운터를 소유하고 응답을 그 세션으로 모은다.
   분산된 가지의 동시 통신에서는 `max(관측한 값)+1`로 올리고 불확실하면 더 큰 값을 택한다. 방어 가능한
   상한을 정할 수 없으면 남은 예산이 있다고 추정하지 않고 10건에 도달한 것으로 취급한다.
5. 10번째 메시지는 전달할 수 있지만 받은 세션은 세션 간 답을 보내지 않는다. 필요한 후속은 아래 사용자
   확인 보고에 포함한다.
6. tx는 판단이 닫히거나, 사용자가 중단·대체하거나, 10건 상한에 도달하거나, 다음 사람 프롬프트가
   도착하면 종료한다. 사람이 계속을 승인하면 같은 판단이어도 새 tx id로 후속 통신을 시작한다. UTC
   날짜를 넘겨 재개하는 통신도 이전 tx를 이어 쓰지 않는다.

### 사람의 마지막 프롬프트 이후 수신 5건

1. 각 세션은 사람이 자기 세션에 직접 보낸 마지막 프롬프트 이후 도착한 세션 간 메시지만 센다. 발신,
   세션 목록·상태 조회, 시스템 알림은 이 카운터에 넣지 않는다.
2. 다른 세션의 메시지나 자동화 신호는 카운터를 초기화하지 않는다. 사람이 그 세션에 새 프롬프트를
   보내면 0부터 다시 센다.
3. 5번째 메시지를 받으면 추가 세션 메시지 전송과 가변 상태 변경을 멈추고 사용자에게 진행 여부를 묻는다.
   읽기 전용 상태 확인과 아래 보고 작성은 허용한다.
4. 사람과 직접 대화할 수 없는 worker는 5번째 메시지에서 멈추고 사람 대면 조정 세션에 같은 보고를
   반환한다. 조정 세션은 이 신호를 다른 작업 결과에 묻지 않고 사용자에게 전달한다.
5. 사용자가 계속을 승인하는 새 프롬프트를 보내면 해당 세션의 수신 카운터는 0으로 돌아가고 후속 세션
   통신은 새 tx로 시작한다. 다른 세션의 메시지나 자동화 신호는 어느 카운터도 초기화하지 않는다.

팬아웃형 협업에서는 tx 총 10건 제한이 먼저 걸릴 수 있고, 두 세션의 깊은 대화에서는 프롬프트 이후 수신
5건 제한이 먼저 걸릴 수 있다. 어느 하나가 걸리면 같은 보고 한 번으로 두 상태를 함께 알린다.

## 중단 시 사용자에게 보고할 내용

`계속할까요?`만 묻지 않고 다음 네 가지를 함께 제시한다.

1. 어떤 제한에 도달했는지와 현재 카운트, 메시지를 보낸 주체(`project-id`와 작업 디렉터리 기준)
2. 지금까지 바뀌거나 검증된 것과 파일·커밋·수치 같은 산출물 포인터
3. 지금 멈추면 잃는 진행 상태 또는 남는 위험
4. 승인을 받으면 바로 수행할 다음 행동 한 줄

## 기록과 canon 승격

위험 경계의 세션 관측과 실제 통신은 각 세션이 자기 journal에 `**SESSION-COMM:**` 한 줄로 기록한다.
절대경로는 공개 기록에 넣지 않고, 작업 디렉터리에서 얻은 `project-id@worktree-or-task`만 남긴다. 형식은
`journal/README.md`를 따른다.

통신 로그 끝에는 파일·커밋·수치 같은 산출물 포인터를 붙인다. 포인터가 없으면 `value:none`, 직접 질문에
대한 답이면 `value:none(direct-answer)`로 적어 새 값이 없는 왕복을 밖에서 구별할 수 있게 한다.

메시지의 답이나 합의가 프로젝트 간 계약, 현재 상태, 하네스 규칙 또는 다른 세션의 후속 작업 근거가 되면
통신 로그로 끝내지 않는다. request 왕복, `changed/`, decision/ADR 또는 관련 canon에 승격하고 통신 로그가
그 포인터를 가리키게 한다. 세션 간 메시지는 정본을 우회하는 비공개 합의 채널이 아니다.

이 형식과 카운터는 이 문서 도입 뒤 새 통신부터 적용한다. 기존 journal과 과거 세션 메시지는 소급해
채우거나 번호를 다시 매기지 않는다.
