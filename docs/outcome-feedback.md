# 검증 결과 기반 지침 개선

## 목적

성공과 실수를 개인·에이전트의 점수가 아니라 지침의 효과를 검토하는 증거로 사용한다. 원시 카운트만으로
규칙을 늘리지 않고, 반복 원인과 변경 전후 재발을 비교해 더 명확하고 실행 가능한 지침을 유지한다.

## 피드백 루프

1. worker는 작업 완료, 리뷰, 검증 또는 승격에서 확인된 결과만 `feedback/`에 기록한다.
2. `operator:feedback-status`는 관찰 기간의 성공·실수 수, major 이상 실수와 반복 `pattern`을 집계한다.
3. curator는 `ATTENTION` 패턴의 실제 원인, 기존 지침, 반례와 적용 범위를 검토한다.
4. 지침의 누락·모호성·과도한 복잡성이 원인으로 확인되면 proposal에 변경안과 기대 효과를 작성한다.
5. 사람의 승인을 받은 변경만 canon 또는 `INDEX.md`에 반영한다.
6. 변경 뒤 같은 `pattern`의 재발과 관련 성공 사례를 관찰해 유지·수정·철회 여부를 판단한다.

## 해석 원칙

- 성공과 실수는 서로 상쇄하지 않는다. 성공이 많아도 major 실수 하나를 숨기지 않고, 실수가 있어도 잘
  작동한 예방 지침을 제거하지 않는다.
- 성공은 일상 행동을 반복 집계하지 않는다. 비직관적 지침이 실제로 도움을 줬거나 명시적 검증을 통과한
  경우처럼 지침 평가에 정보가 있는 결과만 기록한다.
- 실수는 행위자 비난보다 원인 분류에 사용한다. `instruction-missed`, `instruction-ambiguous`,
  `instruction-missing`, `execution-error`, `external-failure`를 구분한다.
- 동일 `pattern`의 수만 보지 않고 어느 승격 단계에서 도입·발견됐는지 함께 본다. 뒤 단계에서 발견될수록
  앞 단계의 체크리스트나 검증 게이트를 우선 검토한다.
- 표본이 작거나 인과관계가 확인되지 않으면 `[미검증]` 저널로 남기고 지침을 바꾸지 않는다.

## 개선 트리거와 조치

`FEEDBACK.md`의 임계값을 기본 트리거로 사용한다.

| 관찰 | 우선 검토 |
|---|---|
| 같은 pattern의 반복 실수 | 관련 작업 지침, 예시, 자동 검사 누락 |
| work에서 도입되어 local-review에서 반복 발견 | 작업 전 체크리스트와 구현 지침 |
| pull-request 또는 feature에서 반복 발견 | 로컬 리뷰 범위와 공동 리뷰 기준 |
| release 또는 canonical에서 반복 발견 | 통합·회귀 검증과 승격 조건 |
| production까지 유출 | 배포 게이트, 롤백과 hotfix 계약 |
| 특정 지침의 반복 성공 | 지침 유지, 간결화 가능성, 자동 검사 승격 |

major·critical 실수는 횟수가 적어도 즉시 검토한다. 단, 외부 실패처럼 지침 변경으로 예방할 수 없는 원인은
복구 절차나 operator 계약의 문제로 보내며 억지로 공통 규칙을 추가하지 않는다.

## 변경 제안의 수용 기준

피드백에서 파생된 proposal은 최소한 다음을 포함한다.

- 관련 event ID와 반복 `pattern`
- 현행 지침의 문제 또는 지침이 없다는 근거
- 바꿀 문장·자동 검사·체크리스트의 정확한 위치
- 불필요한 규칙 증가나 특정 사례 과적합을 막는 범위
- 변경 뒤 확인할 성공 조건과 재발 조건
- 지침을 되돌리거나 다시 검토할 사건 기반 트리거

카운트 임계값은 proposal 생성을 검토하게 하는 신호다. canon 변경의 승인이나 작업 게이트를 대신하지 않는다.
